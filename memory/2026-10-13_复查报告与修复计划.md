## 2. 仍存在的缺陷（本轮全部有实测证据）

### R2-P0-1　加密 PDF：GUI 无密码入口、后台线程收不到密码、另存为/快照静默去掉加密

证据：`memory/repro_encrypted_pipeline.py`（本轮重跑，逐条实测）

```
1) open_file(无密码) = False | openFailed = [('needs_password', ...)]   # GUI 里没有密码输入出口
2) 带密码打开成功、未改动 → _worker_source 返回加密原文件 → 搜索失败：PDF 需要密码
3) 加批注走快照 → 搜索成功，但快照 needs_pass=0 is_encrypted=False     # %TEMP% 落明文
4) save_as 成功 → needs_pass=0 is_encrypted=False                       # 用户以为仍加密
```

根因（三层，互相独立）：

1. `MainWindow._open_path`(:938) 只调 `_controller.open_file(path)`，从不传密码；
   `_on_open_failed`(:1034) 对 `NEEDS_PASSWORD` 仅弹提示。全项目没有任何密码输入框
   （`QInputDialog` 仅用于水印与便签）。控制器早已支持 `password` 形参，GUI 侧没有出口。
2. `SearchWorker.setup(path, query, password=None)` 与 `OcrWorker.setup(..., password=None)`
   **形参存在**，但 `_on_search_requested`(:495)、`_start_ocr`(:811) 从不传入；
   而 `Document`/`DocumentController` 也没有保存过密码，无从传起。
3. `PyMuPdfEngine.save`(:475) 只在**增量保存原文件**时带 `PDF_ENCRYPT_KEEP`；
   整份保存分支 `save(path, garbage=4, deflate=True)` 不带 `encryption` → PyMuPDF 默认写明文
   （`_probe_encrypt_facts.py` 实测 `needs_pass=0`）。`Document.save_copy` 走同一分支，
   于是快照明文落在 `%TEMP%`。

修复所需事实（`_probe_encrypt_facts.py` 实测）：

- `doc.authenticate(pw)` 返回 **0=失败 / 2=用户密码 / 4=所有者密码**，可据此区分权限级别；
- 以所有者密码打开后，用同一密码 `user_pw=owner_pw=pw` + `AES_256` 重写，可正常开；
- 增量保存 + `PDF_ENCRYPT_KEEP` 会同时保留用户密码与所有者密码。

影响：加密文档在 GUI 里**完全不可用**（`tests/integration/test_open_render.py:42` 却宣称支持），
能打开时搜索/OCR/导出也必然失败；另存为与快照会**静默降低安全性**。

### R2-P0-2　中文文本写入静默变成 notdef 方框（水印 / 插入文字）

证据（`_probe_round2b.py` + `_probe_font_embed.py`）：

```
eng.add_text_watermark(doc, 0, '内部机密') → OK（不报错）
eng.insert_text(doc, 0, Point(72,140), '审批通过') → OK
保存后回读：'hello world\n····\n····\n'   含「内部机密」= False  含「审批通过」= False
页面字体：(5, 'n/a', 'Type1', 'Helvetica', 'helv', 'WinAnsiEncoding')
```

根因：`PyMuPdfEngine.add_text_watermark`(:458) 与 `insert_text`(:600) 都调用
PyMuPDF 的 `insert_text(...)` 且**不指定字体**，默认 base-14 `helv`（WinAnsiEncoding）
不含 CJK 字形，PyMuPDF 用 notdef（回读为 `·`）占位，**不抛异常**。
而 GUI 的水印输入框 (`main_window.py:588`) 面向中文用户，插入的正是中文。

修复路径已验证（`_probe_font_fix.py`）：`insert_text(..., fontname="china-s")`（PyMuPDF 内置 CJK）
→ 字体为 `Type0/Heiti/UniGB-UTF16-H`，回读文本正确、2 倍渲染非白像素 1070 → 4084（真实字形），
文件仅增大 1 KB。系统字体文件方案（`msyh.ttc` 嵌入）虽自包含，但**单页从 1.6 KB 涨到 12.4 MB**，
不适合水印场景，需配合 `subset_fonts()` 才可用，故不作为首选。

影响：中文水印/文字插入"看起来成功"，实际页面上是一排方框，且回读/搜索不到该文本。

### R2-P0-3（本轮新发现，已修）旋转页（/Rotate ≠ 0）上取词/搜索必崩，编辑内容还会画错位置

证据：`memory/_probe_rotation_frames.py`（纯 PyMuPDF 事实核对）、
`memory/repro_rotated_page.py`（走本程序 DocumentController：先 monkeypatch 还原旧行为，再跑当前实现）

```
# 引擎 open() 必开 journal，于是旋转页上（旧行为）：
get_words（选择/复制）    → RenderError: 提取第 0 页文本词失败：code=4: Can't alter an object other than in an operation
search（搜索）            → SearchError: 搜索第 0 页失败：同一句
extract_text（导出 TXT）  → RenderError: 同一句
# 写入类不报错，但位置/朝向错（/Rotate=90 的 400x600 页，点在可见 (300,200)）：
时间戳实际渲染在 (400, 291, 440, 300)          ← 跑位，且被转成竖排
签名目标 (120,160,220,210) → 实际渲染成 25x49 竖条并搬到页面另一侧
橡皮擦用可见点查批注 → None（点不中）
```

根因（两层，互相独立）：

1. **读**：PyMuPDF `Page.get_textpage`（`pymupdf/__init__.py:12201`）会先把页面 `/Rotate` 置 0
   建 TextPage、再在 finally 里写回 —— 这是**写 PDF 对象**；而引擎为支持撤销在
   `open()` 里 `journal_enable()`（`pdf_engine.py:290`），MuPDF C 层拒绝 operation
   之外的对象写入。于是 `get_text*` / `search_for` 在 /Rotate≠0 的页上**全部报错**。
   **本程序的「旋转页」功能会把普通页变成这种页，等于自己触发**：转一下页，该页的
   文本选择 / 搜索 / 导出 TXT 立刻全废；而 `DocumentController.get_words` 又把异常吞成
   空词表，界面上只表现为「选不中字」，看不出与旋转有关。
2. **写**：批注与页面内容流按**未旋转帧**存坐标，而渲染位图、页面布局、
   `PdfView._event_to_pdf`（鼠标点击换算）都用**可见帧**（`page.rect`）。两者只在
   /Rotate=0 时重合，于是旋转页上时间戳/签名/手写/便签跑位、橡皮擦点不中、
   高亮「预览画在错地方、提交后落在对地方」。

修复（只在引擎层收口，GUI 无需改动）：

| 文件 | 改动 |
| --- | --- |
| `engines/pdf_engine.py` | 写明旋转页约定；新增 `_normalized_rotation`、`_textpage`（走 `Page._get_textpage`：不写 /Rotate、给出可见帧、journal 开启时安全；若未来该方法被移除，未旋转页退回公开 API、旋转页明确报错而不是返回坐标系不同的数据）、`_unrotated_point` / `_unrotated_points` / `_unrotated_rect` / `_visible_rect`。读路径（`extract_text` / `_extract_spans` / `get_words` / `search`）全部改用 `_textpage`（flags 与原调用点一致，词切分行为不变）；写路径（`add_highlight` / `add_ink` / `add_text_annot` / `insert_text` / `insert_image` / `add_text_watermark`）先 derotate，文字与图片再补 `rotate=page.rotation`（否则被页面旋转带歪）；`annotation_index_at` 折算查询点、`list_annotations` 折算回可见帧 |
| `engines/base.py` | 协议文档逐条写明「坐标一律可见帧」 |
| `scripts/download_samples.py` + `tests/fixtures/samples/rotated.pdf` | 新增旋转页样例（400x600 + /Rotate=90 + 普通页对照） |

### R2-P1-1　视图中已滚过的页面位图永不释放 → 内存随文档页数线性增长

证据（`_probe_round2.py` A，80 页小页文档）：

```
渲染 80 页后：场景中位图项 = 80，LRU 容量 = 30，LRU 实际条目 = 30
已离开视口的第 0 页是否仍被场景持有 = True
is_page_rendered(0)（LRU 视角）= False  ← 已被 LRU 淘汰，重滚回来会重复渲染
```

根因：`PdfView.on_page_rendered`(:628) 把 QPixmap 同时放入 `_rendered_cache`（容量 30）
和 `_page_items[page]`（场景项）。`LRUCache.put` 淘汰条目时**没有任何回调**，
场景里的 `QGraphicsPixmapItem` 仍持有像素，只有该页**再次渲染**或 `invalidate_page`/
下次 `setup_document` 才会替换。于是：

- 内存与"曾经渲染过的页数"同增（实测 A4@150% 单页约 3.4 MB，1000 页 ≈ 3.4 GB）；
- LRU 已淘汰但场景仍持有 → `is_page_rendered()` 为 False → 回滚时**重复渲染**（CPU 白烧）。

这与第一轮修好的 P1-4 是同一族问题的另一半：那次修了"缩放后旧项不清理"，
这次是"滚动后远页不清理"。

### R2-P1-2　搜索线程：`shutdown()` 是空实现 + GUI 阻塞等待 + 陈旧结果覆盖 + 线程对象累积

证据：`_probe_round2b.py` D5 —— 先 `shutdown()` 再 `run()` 依然搜出结果
（`[('ok', 1)]`），证明 `run()` 里**没有任何取消检查点**。

根因：

- `SearchWorker.shutdown`(:47) 只有 `pass`（注释自称"仅为接口一致性"）；
- `MainWindow._on_search_requested`(:486) 却按"能停"来用：`shutdown()` 后 `wait(2000)`
  ——既停不住搜索，又让 GUI 线程最多白等 2 秒（大文档实打实卡顿）；
- 每次搜索都 `SearchWorker(self)` 新建，以 MainWindow 为 parent 且从不回收 → 连续搜索累积 QThread；
- `_on_search_completed`(:499) 不校验 query，也不校验是哪个 worker → 慢文档上先发的旧搜索
  后到会覆盖新结果，用户只看到"找到 N 处结果"，无法察觉（代码走查）。

### R2-P1-3　OCR：不传密码（同 R2-P0-1）、可并发启动、取消却提示"完成"、结果跨运行累积

根因（代码走查，`main_window.py:795-833`）：

- `_start_ocr` 不检查 `self._ocr_worker` 是否仍在运行 → 连点两次 OCR 会开两个线程，
  旧 worker 引用被覆盖，`_on_document_closed`/`closeEvent` 再也 wait 不到它；
- `_ocr_results` 只在打开/关闭文档时清空 → 第二次识别后 `_on_ocr_all_done` 会把上一轮
  各页文本一起拼接展示，但标题写"已识别 N 页"；
- 进度对话框点"取消" → `worker.shutdown()` → 循环 break → 仍 `ocrCompleted.emit(processed)`
  → `_on_ocr_all_done` 弹"OCR 完成！"，用户无法区分"取消"与"完成"；
- 200 DPI 整页直接送 RapidOCR（`OCR_DPI=200`），无边长上限，内存尖峰（第一轮 P1-3 未处理）。

### R2-P1-4　合并后「撤销」静默失效，按钮状态与引擎不同步

证据（`_probe_round2c.py`，GUI 离屏实测）：

```
删页后 undo_action 启用 = True | can_undo = True
合并 2 页 + _refresh_after_edit 后：
  undo_action 启用 = True   ← 引擎 can_undo = False
  redo_action 启用 = False  ← 引擎 can_redo = False
```

根因：`PyMuPdfEngine.merge`(:436) 为绕开 `insert_pdf` 与日志不兼容，会 `tobytes()` 后
**重开文档**（日志随之失效，合并不可撤销）；但 `DocumentController.merge`(:207) 不走 `_run()`，
既不 emit `undoStateChanged`，`MainWindow._on_merge`(:578) → `_refresh_after_edit`(:658)
也不调 `_update_undo_actions()`。于是按钮停留在上一次的启用态，用户点击无任何反应、也无提示。

### R2-P1-5　主线程阻塞：导出转换、打印逐页渲染、快照写出

根因：

- `ExportDialog._on_convert`(:129) 在 GUI 线程直接 `ConvertService.convert`
  （pymupdf/pdf2docx/pdfplumber 都是秒级到分钟级），期间界面完全冻结；
  `services/converter.py:5` 写的"调用方应放在后台线程"没有任何实现，

- `_worker_source`(:508) 在 GUI 线程同步整份 `save_copy`（大文档明显卡顿）。

### R2-P2　搜索质量、脏标记、文档一致性、死代码、覆盖率

1. 搜索结果文本恒为查询词：`PyMuPdfEngine.search`(:403) 传 `text=query`，

   关闭时仍弹保存框。
3. 版本/功能三处不一致：`README.md:4` 写"0.0.1（阶段 0）"，实际 `pyproject.toml:7`、
   `__init__`、`scripts/installer.nsi:14` 都是 0.0.4；CHANGELOG 缺 0.0.3 / 0.0.4 条目；
   README:15 宣称"PDF ↔ Word/Excel/图片/TXT"但 Word→PDF 未实现（`converter.py:14` 自述不支持）；
