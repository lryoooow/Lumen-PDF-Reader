# 项目文件夹结构规划

> 定稿：2026-07-23
> 技术栈：Python + PySide6 + PyMuPDF + RapidOCR
> 设计原则：**分层 + 适配器隔离 + 测试先行 + 渐进式生长**

---

## 一、架构总览

采用经典的**分层架构**，核心思想是**用适配器把第三方引擎（PyMuPDF）隔离在最底层**——这样上层业务逻辑只依赖我们自己的抽象，将来要换引擎、加功能、写测试都不会牵一发动全身。

```
┌──────────────────────────────────────────────────────────┐
│  GUI 表现层 (gui/)      PySide6 控件、窗口、交互          │
│      ↕  Qt 信号/槽                                       │
│  控制器层 (controllers/)  协调 GUI 与业务，处理用户动作    │
│      ↕                                                    │
│  业务核心层 (core/)      框架无关的纯 Python：文档/页面模型│
│      ↕                                                    │
│  服务层 (services/)      重型功能：OCR、格式转换           │
│      ↕                                                    │
│  引擎适配层 (engines/)   封装 PyMuPDF（★隔离第三方）       │
│      ↕                                                    │
│  基础设施 (utils/, config/)  日志、缓存、坐标转换、设置     │
│  后台线程 (workers/)     渲染/OCR/搜索线程（非线程安全隔离）│
└──────────────────────────────────────────────────────────┘
```

### 三条铁律（贯穿整个项目）

1. **`core/` 和 `services/` 绝不 import PySide6 或 PyMuPDF**——它们是纯 Python，可脱离 GUI 独立单元测试。
2. **只有 `engines/` 知道 PyMuPDF 的存在**——所有 `import pymupdf` 只出现在这一个目录。换引擎时改这一个目录即可。
3. **只有 `workers/` 在子线程跑 PyMuPDF**——因为 PyMuPDF 非线程安全，Document 对象的生命周期严格限制在单个渲染线程内。

## 三、关键目录职责详解

### `engines/` — 引擎适配层（最重要的一层）

**职责**：把 PyMuPDF 的 API 翻译成我们自己稳定的接口。**整个项目只有这里 `import pymupdf`。**

```python
# engines/pdf_engine.py（示意，非最终实现）
from __future__ import annotations
from pathlib import Path
import pymupdf  # ← 全项目唯一的 pymupdf 导入点

class PdfEngine:
    """PyMuPDF 的适配器封装。上层只依赖这个类，不碰 pymupdf。"""

    def open(self, path: Path) -> DocumentHandle: ...
    def render_page(self, doc, page_num: int, zoom: float) -> PixmapData: ...
    def extract_text(self, doc, page_num: int) -> str: ...
    def search(self, doc, query: str) -> list[SearchHit]: ...
    def add_highlight(self, doc, page_num, quads) -> None: ...
    def save(self, doc, path: Path) -> None: ...
```

**为什么这样设计**：
- 将来 PyMuPDF 改 API（如 1.24→1.25 的命名变更），只改这一个文件
- 想换引擎（如改用 pypdfium2），只改这一个文件
- 单元测试可以 mock 这个接口，GUI 测试不依赖真实 PDF

### `core/` — 业务核心（纯 Python，无 Qt 依赖）

**职责**：定义领域模型。`Document`、`Page`、`Annotation` 这些是**业务概念**，不是 UI 概念。

**关键**：这一层**绝对不能** `import PySide6`。它用标准库 dataclass / typing。这样：
- 可以脱离 GUI 跑单元测试（快）
- 业务逻辑可复用（比如将来想做命令行版或 Web 版）

### `workers/` — 后台线程（PyMuPDF 非线程安全的解法）

**职责**：把耗时的、非线程安全的操作放到独立 QThread。

**核心约束**：`Document` 对象**只能存在于渲染线程内**，主线程绝不直接持有或操作它。线程间只通过 Qt 信号传递**不可变的结果数据**（如 `QPixmap`、搜索结果列表），绝不传递 `Document` 引用。

### `gui/` — UI 表现层

**职责**：只管"显示"和"接收用户输入"，不含业务逻辑。业务逻辑全部委托给 `controllers/`。

**分层**：
- `widgets/` — 占据主区域的大控件（PDF 视图、缩略图栏）
- `panels/` — 侧边停靠面板（大纲、批注列表）
- `dialogs/` — 模态/非模态对话框
- `components/` — 可复用的小零件（按钮组、颜色选择器）

### `tests/` — 测试（与生产代码同等重要）

**测试分层**：
- `unit/` — 快速单元测试（毫秒级），覆盖 `engines/`、`core/`、`services/`、`utils/`
- `integration/` — 集成测试（真实 PDF 文件 + 多模块协作）
- `fixtures/samples/` — 真实样例 PDF，覆盖各种情况（纯文本/扫描件/表格/带批注）

**测试策略**：**测试先行**。每个模块开发时同步写测试，CI 要求测试全绿才能合并。

## 四、src 布局说明

采用 `src/pdfreader/` 而非顶层 `pdfreader/`：

**好处**：防止"未安装就误导入当前目录代码"的经典坑。强制先 `pip install -e .` 再用，保证测试的是已安装的包，环境和用户一致。

## 五、代码质量工具链（开发前先配好）

| 工具 | 作用 | 配置位置 |
|---|---|---|
| **uv** | 包管理 + 虚拟环境（比 pip 快 10-100 倍，2026 年事实标准） | `pyproject.toml` |
| **ruff** | 格化 + Lint（已取代 black + flake8 + isort 三件套） | `[tool.ruff]` |
| **mypy** | 静态类型检查 | `[tool.mypy]` |
| **pytest** | 测试框架 | `[tool.pytest.ini_options]` |
| **pre-commit** | 提交前自动跑 ruff/mypy | `.pre-commit-config.yaml` |

**强制类型注解**：所有公开函数必须有类型注解（`from __future__ import annotations`），mypy 在 CI 中强制检查。这是"不写出半成品垃圾"的基础保障。

## 六、渐进式生长原则

这个目录结构是**最终形态**。**开发初期不需要一次性建所有目录**——按开发计划的阶段逐步创建：

| 开发阶段 | 这时才创建的目录 |
|---|---|
| 阶段 0（脚手架） | `src/pdfreader/`, `tests/`, 配置文件 |
| 阶段 1（引擎层） | `engines/`, `tests/unit/engines/` |
| 阶段 2（核心模型） | `core/`, `tests/unit/core/` |
| 阶段 3（最小 GUI） | `gui/main_window.py`, `gui/widgets/pdf_view.py` |
| 阶段 4（滚动渲染） | `workers/`, `utils/cache.py`, `utils/coordinates.py` |
| 阶段 5+（功能扩展） | `services/`, `controllers/`, `panels/`, `dialogs/` |
| 阶段 10（发布） | `scripts/`, `resources/i18n/`, 打包配置 |

**不要一上来就建空目录**——空目录是坏味道，说明你在为还没写的代码过度设计。用到才建。
