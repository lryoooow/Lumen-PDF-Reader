# 打包与发布

> 适用版本：Lumen 0.0.6 当前开发分支。产物：程序目录 `dist/PDFReader/` 与安装程序 `dist/PDFReader-Setup-<版本>.exe`。

## 1. 流程

```bash
make check        # 1. 质量门禁全部通过
make icon         # 2. 图标有改动时重新生成 app.ico（可选）
make installer    # 3. PyInstaller 打包 + NSIS 生成安装程序
dist/PDFReader/PDFReader.exe --selftest   # 4. 冻结环境自检（结果写入 %USERPROFILE%\.pdfreader\selftest.json）
```

发布前检查清单：

- [ ] 版本号三处一致：`pyproject.toml`、`src/pdfreader/__init__.py`、`scripts/installer.nsi`
- [ ] `CHANGELOG.md` 已把 `[Unreleased]` 整理为版本条目
- [ ] `make check` 全绿
- [ ] `--selftest` 输出 `"ok": true`（pdf_engine / convert_deps / ocr_engine / ai_deps / research_deps；ai_deps 会真正加载 `_ssl` 并建一个 HTTPS 客户端）
- [ ] 在真机安装后手工验证：打开 / 批注 / 保存、加密文档、OCR、导出、「打开方式」、高分屏显示

## 2. PyInstaller（`scripts/build_windows.py`）

* **onedir**（目录版）：启动快，不必每次解压；作为安装程序的输入。约 410 MB。
* 隐藏导入：rapidocr_onnxruntime、onnxruntime、cv2、pdf2docx、pdfplumber、openpyxl、PySide6.QtPrintSupport。
* `--collect-all`：rapidocr_onnxruntime（OCR 模型 `*.onnx`）、onnxruntime（原生 DLL）、pdf2docx、pdfplumber、
  openpyxl、shapely。
* 打包后自动校验：exe 存在、OCR 模型已打包、onnxruntime DLL 存在、`libcrypto-3-x64.dll` / `libssl-3-x64.dll` / `libffi-8.dll`
  与解释器自带版本逐字节一致（不一致即打包失败）。打包时解释器的 `DLLs` 目录排在 PATH 最前——
  否则在 Git Bash 等环境里会收进 `Git\mingw64\bin` 下同名但不兼容的 OpenSSL，安装后所有 AI 请求报
  「DLL load failed while importing _ssl」。
* 中间产物 `build/` 可随时删除（`make clean`）。

## 3. NSIS 安装程序（`scripts/installer.nsi`）

* 编译器查找顺序：系统 PATH → electron-builder 缓存 `%LOCALAPPDATA%\electron-builder\Cache\nsis\nsis-*\makensis.exe`
  → `C:\Program Files (x86)\NSIS`。本机使用的是放在 electron-builder 缓存中的官方 NSIS 3.10。
* 安装内容：
  * 默认安装到 `C:\Program Files\PDF Reader\`（需要管理员权限，可在向导中修改）；
  * 桌面与开始菜单快捷方式；
  * 「应用和功能」中的卸载项（含版本、大小、图标）；
  * 注册为 `.pdf` 的「打开方式」候选（`OpenWithProgids` + `Applications\PDFReader.exe`），**不抢默认程序**；
* 卸载会删除程序目录、快捷方式与上述注册表项；用户数据 `%USERPROFILE%\.pdfreader\`（设置、日志、阅读位置）保留。
* 覆盖安装：直接运行新安装程序即可，不需要先卸载。
* 安装程序名称、程序目录与 exe 名仍为「PDF Reader / PDFReader」；界面品牌为 Lumen。

## 4. 应用图标

`scripts/make_icon.py` 把 `gui/theme/icons.py` 中的 Lumen 标志（赤陶圆角方块 + 白色衬线「l.」）渲染为
16–256 px 七个尺寸的 `src/pdfreader/resources/icons/app.ico`，供 exe、安装程序与快捷方式使用。窗口内的图标由
同一份 SVG 在运行时渲染，两者保持一致。

## 5. 版本历史说明

品牌更名为 Lumen 后版本号从 **0.0.1** 重新开始；`CHANGELOG.md` 中「Lumen 0.0.1」之下的 0.0.4 / 0.0.2 / 0.0.1
属于旧的「PDF Reader」版本线。

## 6. 原生构建与研究依赖

Windows 安装包仍运行 uv run python scripts/build_windows.py --installer，保留解释器 OpenSSL DLL 字节校验。新增 collect-all：bibtexparser、regex、docx（含默认模板），以及 QtTextToSpeech 隐藏导入。冻结自检增加 research_deps，实际创建中文 DOCX、解析 BibTeX、运行正则并加载朗读模块；不访问真实 AI、不开启音频。

scripts/build_desktop.py 只能在目标系统原生执行，--dry-run 只显示命令。Windows 复用已有 DLL 约束构建，Linux/macOS 用原生 PyInstaller 目录包；自检成功后生成 dist/Lumen-<version>-<platform>-<arch>.zip。macOS 用 scripts/lumen_macos.spec 写入版本和应用标识，最低系统为15.0；Apple芯片与Intel分别原生构建。ditto保留.app框架符号链接、权限和资源，verify_macos_package.py对解压后的实际分发包核对版本、符号链接、临时签名完整性、冻结自检和6秒启动。未使用Developer ID商业签名或Apple公证；Linux需要系统图形/凭据服务。

.github/workflows/build-desktop.yml通过workflow_dispatch选择macos或all；macOS 15的arm64/x86_64分别构建，再在macOS 26双架构复验同一分发包。最低版本以Info.plist为准；兼容目标、实际CI系统和人工验收分开报告，未运行的macOS版本不能写成实测通过。Linux 在独立 D-Bus 会话中启动系统密钥环，使用临时 CI 密码，不使用空凭据后端绕过自检。配置提交不能替代实际工作流成功记录。

Release 应列出实际安装包、校验和、测试与自检结果、功能入口、会话缓存/明文导出边界、AI 核对限制，以及未提供的签名、自动安装更新、云同步和移动端。

macOS目标范围参照[Apple安全更新](https://support.apple.com/en-ph/100100)当前的15/26/27代际，最低构建基线15；新系统仍以实际运行记录为验收依据，不把苹果安全维护范围当作本项目兼容认证。

同版本重新发布使用带构建日期的新标签（如lumen-v0.0.6-build.20261028），应用版本三处仍为0.0.6；保留原标签、Release和校验和，避免让旧下载与新源码混淆。所有本次平台产物校验通过后再发布。

## 7. CircleCI 免费额度构建

ONNXRuntime 从 1.24 起不再发布 Intel macOS 安装包，因此该架构显式使用 1.23 系列，其他平台保留现有锁定版本。依赖安装、真实构建与 OCR 自检均在对应架构执行，不能以其他平台通过替代。

Mac 本地开发、GitHub 手动构建与 CircleCI 构建均以 `uv sync --frozen --no-binary-package pymupdf` 使用新 SWIG 生成 PDF 绑定。仅复验已有 ZIP 的任务不重建该 ZIP。

`.circleci/config.yml` 提供 GitHub Actions 之外的 macOS 构建入口，复用现有打包和分发 ZIP 验证脚本。使用 Free 套餐可用的 `m4pro.medium`：在 macOS 15 镜像构建，再把同一 ZIP 交给 macOS 26 镜像复验。Apple 芯片包原生运行；Intel 包使用独立的 x86_64 Python 与 Rosetta 2 构建、运行，不冒称 Intel 实机验收。镜像没有 Rosetta 时默认明确失败；仅在维护者核对并同意 Apple 许可、手动设置 `accept_rosetta_license=true` 后，才通过 Apple 的 `softwareupdate` 安装到临时 CI 机器，不安装到开发者本机。

Mac 构建作业从锁定的 PyMuPDF 源码包生成原生扩展；`pyproject.toml` 只对 macOS/Python 3.13+ 的构建依赖约束 SWIG 4.4.1，并在测试前核对实际构建版本。原因见上游 [PyMuPDF #4392](https://github.com/pymupdf/PyMuPDF/issues/4392)：旧 SWIG 原生绑定在警告提升为错误时可能崩溃。此处理保留 `-W error` 和全部回归断言，不通过忽略警告绕过。macOS 26 复验使用已经生成的分发 ZIP，不重新打包。

接入时选择本仓库、配置文件 `.circleci/config.yml` 和包含该配置的分支。默认参数 `build_macos=false`，普通提交不执行构建任务；在控制台手动设置布尔参数 `build_macos=true`，并选择 `architecture=arm64`（默认）或 `x86_64`，每次只执行该架构的构建及复验，便于按失败范围重试。不配置定时任务、自动重试、持久依赖缓存、支付方式或自动充值。开始前核对免费额度；如果账户界面提供 Plan → Usage Controls，可缩短临时产物和 workspace 的保存时间，不为此升级套餐。额度不足时停止，不升级套餐继续。

macOS 15 任务保留 ZIP、SHA256、源码提交和解压后验证报告；macOS 26 任务先核对 ZIP 的 SHA256 与源码提交，再复验同一分发包。依赖、检查、打包或自检任一失败均不作为可发布产物。配置语法验证与实际 Mac 构建结果分别记录，接入配置不等于已产出 Mac 安装包。构建成功后下载并核验，再加入现有 Release 草稿，与 Windows 产物一起发布。
